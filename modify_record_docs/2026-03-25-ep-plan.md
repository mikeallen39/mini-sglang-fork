# 2026-03-25 EP Integration Plan

## Goal

规划如何为 `mini-sglang` 的 MoE 模型加入 Expert Parallelism (EP)，起点是当前对
GLM-4.7-Flash / GLM MoE 的支持。

这是一份设计规划，不是实现记录。

## Current State In `mini-sglang`

### What already exists

- Tensor parallelism 已经是主要的分布式抽象。
- MoE 执行已经存在于以下路径：
  - `python/minisgl/layers/moe.py`
  - `python/minisgl/moe/fused.py`
  - `python/minisgl/moe/torch_backend.py`
- 当前分布式通信只暴露了：
  - `all_reduce`
  - `all_gather`

### What does not exist yet

- 还没有 EP 专用的 process group 抽象
- 还没有 expert ownership / local expert mapping
- 还没有用于 EP 的 token dispatcher
- `mini-sglang` 的 distributed layer 中还没有 `all_to_all` 原语
- 还没有支持 EP 的 weight loading 路径
- 还没有支持 EP 的 MoE layer interface

## Key Observation

`mini-sglang` 当前的结构是围绕 TP-first execution 搭建的：

- attention 和 dense layers 都是 TP-aware 的
- MoE 事实上仍然是在每个 TP rank 本地执行，然后再做 reduce
- MoE kernels 假设本地 rank 已经拥有它需要执行的 experts

因此，加入 EP 不是简单地打开一个开关。它需要一种新的执行形态：

1. 将 token 路由到 experts
2. 将 token 分发到拥有这些 experts 的 ranks
3. 只执行本地 experts
4. 将 expert 输出按原始 token 顺序合并回去

## Useful Reference From `sglang`

`sglang` 中与 EP 最相关的部分有：

- EP group abstraction
  - `python/sglang/srt/distributed/parallel_state.py`
- token dispatch / combine
  - `python/sglang/srt/layers/moe/token_dispatcher/standard.py`
  - `python/sglang/srt/layers/moe/token_dispatcher/*`
- 带有 EP-aware local expert count / dispatcher hookup 的 fused MoE layer
  - `python/sglang/srt/layers/moe/fused_moe_triton/layer.py`

其中重要的设计思想是，`sglang` 将以下概念分离开来：

- global expert ids
- rank 上的 local expert ids
- dispatch / combine communication
- local expert kernel execution

而这种分离在 `mini-sglang` 中还不存在。

## Recommended Scope For `mini-sglang`

不要一开始就直接上完整的 `sglang` EP 栈。

合适的路径应该分阶段推进：

### Stage 1: Minimal correctness-first EP

目标：

- 为 MoE 支持 `ep_size > 1`
- attention 和 dense layers 保持当前 TP 路径不变
- 先关注正确性，再关注通信最优性

建议的首批约束：

- 只支持 `ep_size == tp_size`
- 只支持具有连续 ownership 的 routed experts
- shared experts 保持复制
- 暂不支持 EPLB / redundant experts / elastic placement
- 暂不处理 DP-attention coupling

这样可以得到最简单的心智模型：

- 每个 TP rank 拥有 `num_experts / ep_size` 个 routed experts
- router 仍然产出 global expert ids
- 运行时将 global ids 映射为 local ids 或 remote ranks

### Stage 2: Real token dispatch EP

在正确性得到证明之后：

- 加入真正的 token dispatch/combine
- 加入 `all_to_all` 风格的通信
- 避免每个 rank 都执行无用的 experts

### Stage 3: Broader parallel plan

只有在 Stage 2 稳定之后再考虑：

- 支持 `ep_size < tp_size`
- 考虑将 `moe_tp_size` 与 attention TP 分离
- 考虑 DP-attention + EP 组合
- 考虑负载均衡 / expert placement 策略

## Concrete Changes Needed

### 1. Server / Engine Config

增加面向 EP 的配置字段：

- `ep_size`
- 可选的后续字段：`moe_tp_size`

初始校验规则：

- `ep_size in {1, tp_size}`
- 只允许在 MoE 模型上启用 EP
- 初版可以显式拒绝不支持的组合

可能涉及的文件：

- `python/minisgl/engine/config.py`
- `python/minisgl/server/args.py`
- `python/minisgl/engine/engine.py`

### 2. Distributed Groups

增加支持 EP 的 group/state 管理。

至少需要：

- 全局 TP group
- MoE EP group
- 面向 EP 的 rank / world size 辅助函数

初始要求：

- 如果 `ep_size == tp_size`，EP group 可以与当前 TP world 重合
- 但仍要显式暴露 EP helpers，这样其余代码就不会把 TP 假设写死

可能涉及的文件：

- `python/minisgl/distributed/info.py`
- `python/minisgl/distributed/impl.py`
- `python/minisgl/distributed/__init__.py`

### 3. Communication Primitives

当前 `mini-sglang` 的 distributed API 缺少 EP 最关键的通信原语。

需要补充：

- `all_to_all` 或等价的可变尺寸 dispatch API

建议采用分阶段方式：

- 第一阶段的正确性路径：
  - 在 EP ranks 间 `all_gather` hidden states
  - 只执行本地 experts
  - 再将输出 sum / reduce 回去
- 后续再替换为：
  - 真正的 token dispatch
  - 真正的 token combine

原因：

- 以正确性优先的 EP 可以更快基于现有原语落地
- 真正的 `all_to_all` 才是长期正确方案，但一次会引入更多变动点

### 4. MoE Layer Abstraction

当前 `MoELayer` 的假设是：

- 所有本地权重都可以直接执行
- 只需要最后做一次 TP `all_reduce`

这需要被拆分为：

1. router output
2. dispatch
3. local expert execution
4. combine

可能涉及的文件：

- `python/minisgl/layers/moe.py`
- `python/minisgl/moe/base.py`
- `python/minisgl/moe/fused.py`
- `python/minisgl/moe/torch_backend.py`

建议的接口方向：

- 引入 dispatcher object，或支持 EP 的 MoE backend 方法
- 不要把 dispatch 逻辑埋进 Triton kernel wrapper 里

## 5. Expert Ownership / Mapping

需要一套清晰的映射关系：

- global expert id -> owning EP rank
- global expert id -> 该 rank 上的 local expert slot

初始策略应尽量简单：

- routed experts 在各个 EP ranks 之间按连续区间切分
- shared experts 在每个 rank 上本地复制

这套映射应当只创建一次，并在以下场景复用：

- weight loading
- 运行时 topk id 重映射
- 本地 kernel 调用

### 6. Weight Loading

在 EP 下，expert 权重的加载方式必须不同于纯 TP 模式。

对于 routed experts：

- 每个 EP rank 只加载本地 expert 子集

对于 shared experts：

- 要么复制
- 要么在模型需要更复杂处理路径时，初期直接标记为不支持

这意味着 loader 不能再假设每个 rank 都拥有全部 routed experts。

可能涉及的文件：

- `python/minisgl/models/weight.py`

### 7. Model-Specific Integration

GLM 当前有一条自定义模型路径：

- `python/minisgl/models/glm4_moe_lite.py`

需要决定 EP 支持应该放在：

- 通用的 `MoELayer` 中
- 或者部分保留在 GLM-specific code 中

建议：

- 保持 expert dispatch 是通用能力
- 将模型专属代码限制在 router 和 MLA / attention 差异上

## Recommended Implementation Order

### Phase A

增加配置以及 EP group 的基础打通。

Deliverables:

- `--ep-size`
- EP rank / size helpers
- 对受支持组合的显式校验

### Phase B

增加本地 expert ownership 与支持 EP 的 weight loading。

Deliverables:

- 本地 routed expert 数量
- global-to-local expert mapping
- 仅加载本地 expert 权重

### Phase C

在不引入真实 all-to-all 的前提下，增加一条以正确性优先的 EP 执行路径。

可能的临时策略：

- 在 EP ranks 间 gather hidden states 和 router decisions
- 使用重映射后的 local ids 只运行本地 experts
- 将输出再合并回去

这不是最终性能路径，但更容易验证。

### Phase D

将临时 dispatch 路径替换为真正的 token dispatch / combine。

Deliverables:

- 新的 dispatcher abstraction
- `all_to_all` 风格的通信路径
- 在打包后的 dispatched tokens 上执行本地 experts
- 在 combine 期间恢复原始 token 顺序

### Phase E

只有在上述内容稳定之后再做：

- 优化 overlap
- 增加更好的 routing / load balancing
- 扩展到 `ep_size < tp_size`
- 考虑 DP-attention 集成

## Risks

### Biggest technical risk

一开始就试图实现完整性能版本的 EP。

那会把太多改动同时耦合在一起：

- groups
- weight loading
- routing semantics
- dispatcher
- kernel expectations
- output combine

很可能的结果就是进入一个漫长且不稳定的调试周期。

### Biggest design risk

在 ownership / dispatch 模型尚未清晰之前，就把 TP 和 EP 逻辑直接混入现有的
fused MoE kernels。

系统需要在以下边界上保持显式分离：

- global routing ids
- local expert ids
- dispatch transport
- local execution

## Recommended First Milestone

`mini-sglang` 中 EP 的第一个里程碑应当是：

- GLM/Qwen/DeepSeek 风格的 MoE 模型
- `ep_size == tp_size`
- 仅加载本地 expert 权重
- 以正确性优先的 dispatcher 路径
- 一个证明 EP 能生成合理输出的真实功能测试

只有完成这些之后，项目才应该尝试更快的真实 dispatch 路径。
